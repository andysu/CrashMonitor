# CrashMonitor v2 — Система глибокого моніторингу та діагностики збоїв Windows Server

CrashMonitor v2 — це автономний комплекс моніторингу типу «чорна скринька літака» (Flight Recorder) для Windows Server 2022. Він розроблений для розслідування раптових самовільних перезавантажень, апаратних скидань (Reset), знеструмлень, зависань накопичувачів та синіх екранів смерті (BSOD / BugCheck).

Система працює 24/7 у фоновому режимі як служба через планувальник завдань Windows від імені `NT AUTHORITY\SYSTEM`, фіксує передісторію роботи сервера з високою роздільною здатністю (кожні 3 секунди) і гарантує збереження доказів у разі раптового краху.

## Архітектура та принцип роботи

Система побудована за 3-рівневою моделлю процесів для ізоляції збоїв:

```
                          [ Scheduled Task: CrashMonitor_AutoStart ]
                                             │
                                             ▼
                               [ CrashMonitor.ps1 ] (Supervisor)
                         ┌───────────────────┴───────────────────┐
                         │                                       │
     [ Worker.ps1 -Role telemetry ]             [ Worker.ps1 -Role events ]
     • CPU, RAM, Disk Queue, Latency            • System & Application logs
     • 40+ Hardware Sensors (Ring-0)            • WHEA hardware error XML
     • processes-latest.json snapshot           • New-CMIncident (crash packs)
     • Запис telemetry-v2.csv (3s)              • Ротація & обрізання кожні 60s
```

1. **Супервізор (`CrashMonitor.ps1`)**:
   - Запускається при старті ОС (Boot Trigger) ще до входу користувача.
   - Генерує унікальний ідентифікатор сесії завантаження (`BootKey`) та ідентифікатор запуску (`MonitorSessionId`).
   - Веде незалежний високопріоритетний пульс системи (`Evidence/Logs/heartbeat-v2.csv`). Якщо вся система чи диски зависнуть — за перерваним пульсом визначається точна секунда смерті ОС.
   - Контролює воркерів: якщо будь-який збирач завис або завершився через помилку WMI/CIM, супервізор автоматично перезапускає його без зупинки моніторингу.
2. **Збирач телеметрії (`Worker.ps1 -Role telemetry`)**:
   - Опитує лічильники ОС кожні 3 секунди з жорсткими таймаутами (4 секунди), щоб збій підсистеми не заблокував збір.
   - Зчитує апаратні напруги, температури, струми й вентилятори через бібліотеку ядра.
   - Робить запис проби дискової затримки (`io-probe.tmp`), фіксуючи мікрозависання контролера SSD/HDD перед падінням.
   - Зберігає повний зріз усіх процесів ОС (PID, RAM, CPU, дескриптори) у `Evidence/Logs/processes-latest.json`.
3. **Збирач подій та інцидентів (`Worker.ps1 -Role events`)**:
   - Читає події Windows (`System`, `Application`, `WHEA-Logger`, `BugCheck`, `Kernel-Power`).
   - Зберігає повні необрізані XML подій та бінарні `WHEA RawData`.
   - При старті після збою класифікує причину рестарту і формує повний ізольований пакет інциденту в `Evidence/Incidents/<BootKey>/`.
   - Щойно відбулася хвилина роботи — викликає ротацію й ковзне обрізання старих логів.
4. **Стійкість файлів стану (`Write-CMJson` / `Read-CMJson`)**:
   - Стан (`worker-*.json`, `health.json`, курсори) пишеться атомарно через `File.Replace`. Читачі відкривають файл із `FileShare.ReadWrite | Delete`, тож не блокують заміну; запис і читання повторюють спробу кілька разів (до ~1 с), якщо файл коротко тримає інший процес (антивірус, стороння утиліта) або він саме замінюється.
   - Запис стану воркера (`Write-ProgressState`) і heartbeat/`health.json` супервізора ніколи не зупиняють процес: помилка пишеться в журнал як `WARNING`. Раніше збіг запису воркера з читанням супервізора міг мовчки завершити воркер (робоча станція, 2026-10-13); у 10-секундній навантажувальній перевірці у двох процесах старий код мав 24 невдалі записи, новий — 0.
5. **Міжпроцесна синхронізація (`Invoke-CMFileLock`)**:
   - Усі операції запису та ротації використовують глобальні іменовані м'ютекси Windows (`Global\CMFile_<hash>`). Конфлікти блокування файлів між супервізором і збирачами виключені.

## Детальний опис кожного файлу

### 1. Кореневі виконавчі файли
- [`CrashMonitor.ps1`](CrashMonitor.ps1) — **Головний супервізор**. Перевіряє єдиний екземпляр процесу, реєструє сесію завантаження, запускає фонових воркерів, безперервно пише `heartbeat-v2.csv` та стежить за станом збирачів.
- [`Worker.ps1`](Worker.ps1) — **Універсальний воркер**. Запускається параметризовано: `-Role telemetry` або `-Role events`. Реалізує цикл збору, контроль вільного місця на диску та оновлення стану прогресу.
- [`Install.ps1`](Install.ps1) — **Скрипт інсталяції та оновлення**. Створює системну задачу в Планувальнику завдань (`CrashMonitor_AutoStart`), налаштовує параметри аварійних дампів пам'яті (опціонально `-EnableCrashDumps`) і робить резервні копії перед зміною файлів. Встановлює на `RootPath` явні права доступу без успадкування від `C:\` (`Set-CMRootAcl`): `Administrators` і `SYSTEM` — повний доступ, `Users` — лише читання й виконання. Логіку перевірки пакета, диференційного бекапу `Tools/`, прав доступу та реєстрації задачі винесено у функції `Assert-CMPackageManifest`, `Test-CMToolsChanged`, `Set-CMRootAcl`, `Register-CMAutoStartTask` на початку скрипта. Після зміни будь-якого файлу з `manifest.json` потрібно перегенерувати маніфест скриптом [`Scripts/Update-Manifest.ps1`](Scripts/Update-Manifest.ps1), інакше інсталяція зупиниться з `Package checksum mismatch`.
- [`manifest.json`](manifest.json) — **маніфест цілісності пакета**: розмір і SHA-256 файлів пакета: `*.ps1` у корені, `Modules/*.psm1`, `Scripts/*.ps1`, `Tests/*.ps1`, `Config/*.json`, усе в `Tools/` (включно з драйвером `Tools/LibreHardwareMonitor/LibreHardwareMonitor.sys`), `.gitattributes`, `.gitignore`. `Install.ps1` перевіряє його до будь-яких змін у системі. `README.md` і `TODO.md` до маніфесту не входять, щоб правки документації не вимагали його перегенерації. Файл не редагується вручну — лише через `Scripts/Update-Manifest.ps1` (див. «Оновлення маніфесту пакета»).
- [`NightlyLogCleanup.ps1`](NightlyLogCleanup.ps1) та [`RegisterNightlyTask.ps1`](RegisterNightlyTask.ps1) — сумісні заглушки старого нічного планувальника v1 (деактивовані, оскільки v2 виконує розумне ковзне очищення автоматично щохвилини).

### 2. Модулі ядра (`Modules/`)
- [`Common.psm1`](Modules/Common.psm1) — **Базова бібліотека спільних функцій**:
  - `Write-CMCsv`: потоковий запис CSV з обов'язковим екрануванням лапок, invariant крапкою в десяткових числах та перевіркою схеми заголовків.
  - `Invoke-CMFileLock`: міжпроцесне блокування на базі системних м'ютексів.
  - `Get-CMBootInfo`: зчитування контексту завантаження ОС (`BootKey`, час старту).
  - `Get-CMRestartClassification`: евристичний аналізатор подій для визначення типу перезавантаження (`Bugcheck`, `UnexpectedReset`, `RequestedRestart`, `Unknown`).
  - `Invoke-CMRotation`: серце ротації — перевіряє ліміти розміру та викликає очищення.
  - `Limit-CMCsvLog` та `Limit-CMTextLog`: функції ковзного часового зрізу — тримають у файлах CSV лише свіжі записи за останні `RetentionHours` (4 години), відкидаючи старі рядки без зупинки запису.
- [`TelemetryV2.psm1`](Modules/TelemetryV2.psm1) — **Збирач продуктивності**:
  - `HardwareSensorsJson` у `telemetry-v2.csv`: повний `RawSummary` датчиків раз на `SensorFullSummaryIntervalSeconds` (30 с), між ними — лише температури, напруги, потужність і оберти вентиляторів (`RawSummaryScope: Essential`): рядок ~4,3 КБ замість ~6,8 КБ. При 6,8 КБ чотири години замірів по 3 с (32,6 МБ) перевищували `MaxLogSizeMB: 32`, і ротація переносила передісторію збою в архів. Віддалений пакет і тривоги отримують повні значення.
  - Лічильники CPU, пам'яті й дисків читає через постійні об'єкти `PerformanceCounter` (`UsePerformanceCounters: true`): створюються один раз при старті воркера, набір дисків оновлюється, коли змінюється список екземплярів. Замір на робочій станції — ~150–200 мс замість ~1 050 мс через WMI, а швидкості (байти/с, сторінки/с, CPU %) усереднюються за весь інтервал між замірами. Інтервал 1 с можна задати через `SampleIntervalSeconds: 1`; типово 3 с.
  - Запасний шлях — класи WMI/CIM `Win32_PerfFormattedData_PerfOS_Processor`, `Win32_OperatingSystem`, `Win32_PerfFormattedData_PerfOS_Memory`, `Win32_PerfFormattedData_PerfDisk_PhysicalDisk`, `Win32_PerfFormattedData_Counters_ProcessorInformation`: використовується, якщо лічильники недоступні (англійські назви лічильників можуть бути відсутні на деяких локалізованих системах) або `UsePerformanceCounters: false`. Джерело пишеться в `telemetry.log` при старті воркера (`counter source: PerformanceCounter|WMI`).
  - `ProcessorPerformancePct` (остання, 24-та колонка `telemetry-v2.csv`) — `% Processor Performance`: фактична частота відносно базової. Понад 100 — турбо; нижче 100 під навантаженням — тротлінг через температуру або ліміт живлення; на простої низькі значення нормальні (енергозбереження). Колонку додано в кінець, тож номери наявних колонок не змінилися; старий `telemetry-v2.csv` з 23 колонками супервізор при старті переносить в `Evidence/Archive/`.
  - `Initialize-CMTelemetry`: при старті воркера (фаза `WarmingUp`) робить один пробний запит до лічильника CPU з таймаутом 30 с. Перший WMI-запит до лічильників продуктивності в процесі найповільніший і при старті служби під навантаженням перевищував таймаут 4 с, через що перший рядок телеметрії мав `CPU: Timed out`. Тривалість прогріву або помилка пишуться в `Evidence/Logs/telemetry.log`.
  - Здійснює Storage I/O Probe (`io-probe.tmp` із примусовим `Flush`) для виявлення підвисань дискового контролера.
  - Збирає повний зріз процесів ОС та викликає `VoltageMonitor.psm1`.
  - Записує виділений лог температур `Evidence/Logs/temperatures.csv` (`Get-CMStorageTemperatures`): спершу Samsung 980 і ST1000 (сервер), а якщо їх немає — перший NVMe і перший HDD за `Get-PhysicalDisk` (будь-який виробник).
  - Формує тривоги (`Get-CMSensorAlerts`): температура >= 70°C та вихід ліній +12V/+5V/+3.3V за допуск ATX ±5%. У `telemetry.log` тривога пишеться один раз при появі та один раз при зникненні (`Sensor alert cleared`), а не на кожному замірі; самі значення лишаються в `telemetry-v2.csv`. `Distance to TjMax` (запас до порогу тротлінгу Intel) не вважається температурою. Непідключені входи Super I/O, що показують випадкові значення, вимикаються списком `IgnoredTemperatureSensors` у `config.json`.
- [`VoltageMonitor.psm1`](Modules/VoltageMonitor.psm1) — **Модуль низькорівневих апаратних сенсорів (Ring-0)**:
  - Динамічно завантажує C#-інтерфейс до бібліотеки `LibreHardwareMonitorLib.dll`.
  - Ініціалізація (компіляція `Add-Type` і завантаження драйвера, ~13 с на робочій станції) виконується у фоновому runspace того самого процесу (`Get-CrashMonitorVoltageSnapshot -Background`), тож заміри після старту воркера не затримуються: поки вона триває, телеметрія пишеться без апаратних датчиків зі статусом `TemperatureStatus: SENSORS_INITIALIZING` (або `ACPI_WMI`, якщо доступний ACPI), а датчики з'являються в першому замірі після готовності. Невдала ініціалізація дає `DISABLED` і не повторюється на кожному замірі.
  - Опитує Super I/O мікросхему материнської плати (Nuvoton) та MSR-регістри процесора Intel Core i5.
  - Повертає напруги ліній БЖ (`Vcore`, `+3.3V`, `AVCC`, `3VSB`, `VBat`, `VTT`), оберти вентиляторів, температури окремих ядер та енергоспоживання процесора у ватах.
  - Зіставлення написане під сервер (Intel i5-9400, NCT6796D, Samsung 980); ці правила мають пріоритет, а їх результат зафіксовано тестом. Для AMD є запасні правила, що заповнюють лише те, що лишилось `N/A`: `CpuTemp` з `Tctl/Tdie`, `CpuPower` з `Power_Package`, `Vcore` з `SVI2_TFN` (вхід Vcore чипа Nuvoton на AMD-платах залежить від плати й може показувати хибне значення). `+12V`/`+5V` без відомого дільника лишаються `N/A`.
- [`EventCapture.psm1`](Modules/EventCapture.psm1) — **Збирач журналів подій**:
  - Зчитує канали подій `System`, `Application` та специфічні провайдери.
  - У `System`, крім помилок, збираються апаратні попередження й інформаційні події, прив'язані до провайдера: `disk 51` (помилка I/O під час підкачки), `Ntfs 50/98/140` (втрачений відкладений запис, перевірка тому, збій скидання на диск), `Display 4101` (перезапуск драйвера GPU), `Kernel-General 1` (зміна системного часу). Журнал подій Windows відхиляє XPath, у якому понад ~22 умови через `or`, тому для `System` будується `QueryList` із двома `Select` — Windows повертає їх об'єднання в порядку записів.
  - Апаратні журнали з `HardwareEventChannels` у `defaults-v2.json` (журнал, максимальний рівень, необов'язковий фільтр `EventData`): `Kernel-WHEA/Errors`, `Kernel-WHEA/Operational`, `Kernel-Power/Thermal-Operational`, `Ntfs/Operational` (попередження й помилки), `Storage-ClassPnP/Operational` (лише помилки, без «немає носія» `SenseKey 2 / ASC 58` від порожніх гнізд кардрідера та без непідтримуваних команд `SenseKey 5`). Відсутні в цій версії Windows журнали пропускаються. Ключ задано в типових налаштуваннях, тож він діє і на вже встановлених копіях. Ці журнали з тими самими фільтрами потрапляють і в EVTX інцидентного пакета.
  - Підтримує курсори читання (`cursor-*.json`) для збереження позиції між перезапусками монітора.
  - Зберігає повні оригінальні XML подій (включно з необрізаними бінарними `RawData` для апаратних помилок WHEA).
- [`Diagnostics.psm1`](Modules/Diagnostics.psm1) — **Пакетувальник інцидентів та звітів**:
  - Здоров'я накопичувачів (`Invoke-CMStorageHealthSnapshot`, воркер подій): при старті та кожні `StorageHealthIntervalMinutes` (15 хв) пише рядок на кожен диск у `Evidence/Logs/storage-health.csv` — лічильники надійності Windows (`Get-StorageReliabilityCounter`: помилки читання/запису, максимальні затримки, температура, знос) та, якщо є `Tools/smartmontools/smartctl.exe`, атрибути SMART: 5 переназначені сектори, 197/198 нестабільні й невиправні, 199 помилки CRC (кабель), 188 таймаути команд, 187, 192 аварійні вимкнення, а для NVMe — помилки носія, журнал помилок, критичне попередження, резерв і знос. Атрибут 192 не вважається лічильником аварійних вимкнень, якщо дорівнює 193 (так Toshiba DT01ACA100 повторює в ньому кількість паркувань головок: 51 281 = 51 281); атрибут 188 Seagate розпаковується (raw `2 2 5` → 5). Дані зіставляються з диском за серійним номером, а для NVMe, де серійні номери з двох джерел різняться, — за унікальною назвою моделі. Зростання лічильників помилок, зміна `HealthStatus` або провал SMART пишуться в `events.log` як `Storage health change`, а зміни між останнім знімком до перезавантаження і першим після нього потрапляють у `report.json`/`report.txt` інцидентного пакета (`StorageHealthChanges`) разом із хвостом `storage-health.csv`. Знімок триває кілька секунд, тому виконується у воркері подій, а не в циклі телеметрії.
  - `New-CMIncident`: генерує детальний автономний інцидент при виявленні перезапуску: експортує EVTX, збирає знімок конфігурації заліза (`inventory.json`), записує хвіст телеметрії (300 точок до збою) та виносить фінальний вердикт.
  - `Export-CMDiagnostics`: упаковує всі матеріали розслідування в єдиний ZIP-архів із SHA-256 маніфестом цілісності.

### 3. Скрипти діагностики та перевірки (`Scripts/`)
- [`Find-CrashPatterns.ps1`](Scripts/Find-CrashPatterns.ps1) — **Аналізатор закономірностей перезавантажень**. - [`Config/config.json`](Config/config.json) — діюча конфігурація монітора (підтримує `EnableUdpHeartbeat`, `UdpHeartbeatHost`, `UdpHeartbeatPort`, `IgnoredTemperatureSensors`). `IgnoredTemperatureSensors` — список шаблонів PowerShell `-like` для ключів датчиків, що не повинні викликати тривогу перегріву, наприклад `["*NCT6798D_Temperature_Temperature_3"]`. За замовчуванням порожній; заповнюйте лише для входів, непідключеність яких перевірено (наприклад, у BIOS вони не відображаються).

  - Вимірювання на робочій станції (306 процесів): повний цикл телеметрії ~1,1 с, з яких ~850 мс — три WMI-запити до форматованих лічильників продуктивності; запис CSV/JSON — ~70 мс. Тобто інтервал 3 с має запас.

## Метрики та апаратні сенсори (Ring-0)

CrashMonitor зчитує понад 40 апаратних метрик. Частина з них (диски, ОС, мережа) доступні через стандартні API Windows, але низькорівневі напруги БЖ та прямі температури ядер вимагають виконання процесорних інструкцій `rdmsr` та `in/out`, що заборонено у звичайному просторі додатків (Ring-3).

### Як реалізовано доступ до Ring-0:
1. Використовується бібліотека [`Tools/LibreHardwareMonitor/LibreHardwareMonitorLib.dll`](Tools/LibreHardwareMonitor/LibreHardwareMonitorLib.dll).
2. Бібліотека завантажує драйвер режиму ядра `WinRing0`.
3. Оскільки Microsoft Defender за замовчуванням блокує цей драйвер як застарілий за правилом вразливих драйверів (**`VulnerableDriver:WinNT/Winring0`**, Threat ID `2147937641`), у Defender було внесено цільовий дозвіл саме для цього ідентифікатора загрози:
   ```powershell
   Set-MpPreference -ThreatIDDefaultAction_Ids 2147937641 -ThreatIDDefaultAction_Actions 6
   Add-MpPreference -ExclusionPath "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.sys"
   ```
   *Це налаштування зберігається в системному реєстрі назавжди і не скидається після перезавантаження сервера.*

### Що зчитується завдяки цьому:
- **Материнська плата (Nuvoton NCT6796D):**
  - Напруга живлення процесора: `Vcore` (0.65 – 1.10 V)
  - Лінії живлення плати: `+3.3V`, `AVCC` (3.3V), `3VSB` (3.3V), `VTT` (1.06V)
  - Батарейка CMOS на платі: `VBat` (~3.1 V)
  - Оберти процесорного вентилятора: `Fan 2` (~1320 RPM)
- **Процесор Intel Core i5-9400:**
  - `CPU Package Temperature`: загальна температура кристала
  - Температури кожного з 6 ядер окремо (Cores 1–6)
  - Відстань до тротлінгу / критичної межі: `Distance to TjMax`
  - Споживання потужності: `CPU Package Power` (Watt), `Cores Power` (Watt), `Memory Controller Power` (Watt)
  - Тактові частоти кожного ядра (MHz) та напруги VID
- **Накопичувачі (Samsung 980 NVMe & Seagate HDD):**
  - Температура NAND пам'яті NVMe та окремо температура контролера NVMe (Controller Temp)
  - Запас комірок пам'яті (Available Spare %), відсоток зносу (Percentage Used)
  - Прочитано / записано гігабайт за весь час життя
  - Температура жорсткого диска HDD

## Безпека та ризики (Security Advisory: WinRing0)

> [!WARNING]
> Драйвер `WinRing0`, який використовується цією збіркою LibreHardwareMonitor, має публічно задокументовану вразливість **CVE-2020-14979** (Local Privilege Escalation). Через відкритий інтерфейс драйвера локальний зловмисник без адміністративних прав може прочитати або змінити фізичну пам'ять ядра.

- **Чому це заблоковано типово:** Microsoft Defender блокує драйвер через сигнатуру `VulnerableDriver:WinNT/Winring0` у списку блокування вразливих драйверів (Vulnerable Driver Blocklist).
- **Коли це безпечно:** На виділеному сервері або стенді, де до системи мають доступ виключно адміністратори (немає сторонніх локальних облікових записів або сервісів з низькими привілеями), увімкнення цього драйвера є контрольованим компромісом для отримання критичної телеметрії напруг БЖ.
- **Права на теку монітора:** код у `RootPath` виконується від імені SYSTEM і завантажує драйвер ядра. Якщо звичайний користувач може змінювати ці файли, він отримує права SYSTEM навіть без вразливості драйвера. Версії `Install.ps1` до 2026-10-13 залишали успадковані права `C:\` (`Authenticated Users: Modify`). Поточна версія обмежує їх (`Set-CMRootAcl`); на вже встановлених системах права оновлюються повторним запуском `Install.ps1`. Перевірка: `icacls C:\CrashMonitor` має показувати лише `Administrators`, `SYSTEM` (F) та `Users` (RX) без позначки `(I)`.
- **Альтернатива без ризику:** Якщо корпоративні політики забороняють винятки Defender:
  1. Можна вимкнути апаратні сенсори: `"EnableHardwareSensors": false` у [`Config/config.json`](Config/config.json).
  2. Використовувати безпечний штатний датчик ACPI через Windows WMI (`MSAcpi_ThermalZoneTemperature`), який працює на рівні системи без сторонніх драйверів ядра.

## Ковзне вікно логів та збереження інцидентів

Для розслідування раптових перезавантажень не потрібні гігабайти рутинних логів за попередні тижні — критично важлива **детальна передісторія за останні кілька годин безпосередньо перед моментом збою**.

### Механізм ковзного вікна (`RetentionHours = 4`):
1. У [`Config/config.json`](Config/config.json) встановлено параметр `"RetentionHours": 4`.
2. Щохвилини воркер подій викликає функцію `Invoke-CMRotation`.
3. Функція `Limit-CMCsvLog` аналізує стовпець `Utc` у потокових CSV-файлах (`telemetry-v2.csv`, `temperatures.csv`, `heartbeat-v2.csv`) із точним приведенням до шкали UTC (`DateTimeOffset`).
4. Усі рядки, старіші за `(UtcNow - 4 години)`, потоково відкидаються.
5. Якщо сервер був тривалий час вимкнений і всі рядки в лозі застарілі, функція гарантовано зберігає останні 300 рядків як опорну точку.
6. Файли завжди містять останні ~4800 точок вимірювання (за 4 години), не розростаються понад розумні межі (тримаються в межах 20–30 МБ) і моментально відкриваються для аналізу.

### Недоторканність аварійних інцидентів:
Коли на сервері стається аварійне вимкнення, перезапуск або синій екран:
- Створюється окрема постійна папка в `Evidence/Incidents/<BootKey>/`.
- У неї назавжди зберігаються: повні логи подій навколо збою, EVTX, дампи WHEA, знімок конфігурації та **300 рядків телеметрії прямо перед моментом смерті ОС**.
- Ротація ковзного вікна **ніколи не видаляє** папки інцидентів (вони зберігаються до ліміту `MaxIncidents: 100`).

## Класифікація перезавантажень

При кожному новому старті CrashMonitor аналізує журнали подій Windows і автоматично класифікує попереднє вимкнення:

| Тип вердикту | Значення | Що це означає |
| :--- | :--- | :--- |
| **`Bugcheck`** | Синій екран (BSOD) | Windows зафіксувала stop error, записала BugCheck код і дамп пам'яті (`C:\Windows\Minidump`). |
| **`RequestedRestart`** | Штатний рестарт | Зафіксовано подію `User32` (подія 1074) — перезавантаження ініційовано користувачем, службою оновлення або скриптом. |
| **`UnexpectedReset`** | Апаратний Reset / БЖ | Зафіксовано `Kernel-Power 41` без жодного коду помилки. Свідчить про зникнення живлення, кнопку Reset, спрацювання захисту БЖ або миттєвий апаратний перезапуск материнської плати. |
| **`Unknown`** | Недостатньо даних | Немає чітких слідів завершення. |

## Швидкий старт та щоденні команди

Всі команди виконуються у **PowerShell від імені Адміністратора**:

### 1. Перевірити живий стан сенсорів прямо зараз:
```powershell
powershell -ExecutionPolicy Bypass -File .\Scripts\Watch-LiveSensors.ps1
```
*(Для безперервного спостереження кожні 3 секунди: додайте `-Samples 100`)*

### 2. Перевірити статус служби CrashMonitor:
```powershell
powershell -ExecutionPolicy Bypass -File .\Scripts\Get-MonitorStatus.ps1
```

### 3. Запустити вбудовані тести самоперевірки:
```powershell
powershell -ExecutionPolicy Bypass -File .\Tests\Test-Self.ps1
```

### 4. Зібрати повний діагностичний ZIP-пакет для аналізу:
```powershell
powershell -ExecutionPolicy Bypass -File .\Scripts\Export-Diagnostics.ps1
```
*(Готовий архів буде збережено в каталозі `Exports/`)*

### 5. Зупинити або перезапустити моніторинг:
```powershell
# Штатна зупинка:
powershell -ExecutionPolicy Bypass -File .\Scripts\Stop-Monitor.ps1

# Запуск через планувальник:
Start-ScheduledTask -TaskName "CrashMonitor_AutoStart"
```

   - Відкрийте [`Modules/VoltageMonitor.psm1`](Modules/VoltageMonitor.psm1).
   - У методі `ReadAllSensors()` словник `dict` містить усі доступні сенсори LibreHardwareMonitor.
   - Щоб додати новий параметр (наприклад, окремі напруги 12V/5V або температури додаткових дисків), додайте відповідні ключі в хеш-таблицю `$snapshot` у функції `Get-CrashMonitorVoltageSnapshot`.
2. **Зміна часу зберігання логів**:
   - У файлі [`Config/config.json`](Config/config.json) змініть значення `"RetentionHours"`. Наприклад, `"RetentionHours": 8` зберігатиме історію за останні 8 годин.
3. **Додавання нових каналів Windows Event Log**:
   - У файлі [`Config/config.json`](Config/config.json) у масив `"OptionalEventChannels"` додайте потрібний журнал (наприклад, `"Microsoft-Windows-Storage-Storport/Operational"`).
4. **Перевірка після змін**:
   - Після будь-якої модифікації коду обов'язково виконайте:
     ```powershell
     powershell -ExecutionPolicy Bypass -File .\Tests\Test-Self.ps1
     ```
   - Тест перевіряє сумісність синтаксису, роботу блокувань, парсерів та експорту і захищає від внесення регресійних помилок.
5. **Оновлення маніфесту пакета** (після зміни коду, конфігурації чи `Tools/`, перед комітом):
   - Перевірити, чи маніфест актуальний (нічого не записує; код виходу 1, якщо є розбіжності):
     ```powershell
     powershell -ExecutionPolicy Bypass -File .\Scripts\Update-Manifest.ps1 -Check
     ```
   - Перегенерувати `manifest.json`:
     ```powershell
     powershell -ExecutionPolicy Bypass -File .\Scripts\Update-Manifest.ps1
     ```
   - Команди виконуються з кореня проекту (наприклад, `C:\Users\andy\CrashMonitor`) і не потребують прав адміністратора. Скрипт можна запускати з будь-якої теки: корінь визначається за його власним розташуванням, або явно через `-RootPath "<шлях до проекту>"`.
   - Pre-commit hook [`.githooks/pre-commit`](.githooks/pre-commit) виконує `Update-Manifest.ps1 -Check` автоматично і блокує коміт, якщо маніфест застарів. Коміти, що змінюють лише `*.md`, перевірку пропускають. Хук перевіряє робочу теку, тому незакомічені зміни в файлах пакета теж враховуються. Обійти перевірку можна через `git commit --no-verify`, але лише свідомо: інакше `Install.ps1` відмовить у встановленні.

## Зовнішній запис пульсу

Під час раптового скидання або втрати живлення останні секунди локальних журналів можуть не потрапити на диск. Запис на іншому пристрої цього не залежить.

**Що надсилає сервер** (UDP, формат syslog RFC 5424 з JSON у тілі — його приймає і будь-який syslog-сервер роутера чи NAS):
- `hb` — від супервізора кожні `HeartbeatIntervalSeconds` (2 с): `Seq`, `BootKey`. Його зникнення — момент зупинки системи; воркери тут ні до чого.
- `telemetry` — від воркера телеметрії кожен замір: CPU %, RAM, черга й затримка диска, `CpuTempC`, `CpuPowerW`, `Vcore`, `Plus12V`/`Plus5V`/`Plus33V` (якщо відомі), `FanRpm`, `DiskTempC`, а також лічильники апаратних подій від старту системи: `Whea`, `StorageErrors` (диск/NTFS/контролери, ClassPnP), `ThermalEvents` (тротлінг, температурні події). `Ntfs 147` (I/O довше 30 с) не враховується, якщо без часу сну затримка була б нижчою за поріг: NTFS рахує настінний час, і запит, виданий перед сном S3, «триває» весь сон (на робочій станції 5 подій по ~18 014 000 мс за 5 год сну). Межі сну беруться з `Power-Troubleshooter 1` (`SleepTime`/`WakeTime` в UTC; час самих подій навколо пробудження ненадійний, доки годинник не синхронізується). Підсумок `Ntfs 149` враховується лише за реальних збоїв читання/запису чи переназначення кластерів. Лічильники веде воркер подій у `Evidence/State/hardware-event-counts.json`.

**На комп'ютері-приймачі** (Windows, PowerShell 5.1+): скопіювати `Scripts/Receive-Heartbeat.ps1` і запустити:
```powershell
powershell -ExecutionPolicy Bypass -File .\Receive-Heartbeat.ps1 -Port 514 -OutputDirectory D:\HeartbeatLogs -SilenceSeconds 10
```
Вхідний UDP на цей порт має дозволити брандмауер приймача (від адміністратора, один раз):
```powershell
New-NetFirewallRule -DisplayName 'CrashMonitor heartbeat' -Direction Inbound -Protocol UDP -LocalPort 514 -Action Allow
```
Результат: `heartbeat-<сервер>.csv` — кожен пакет; `heartbeat-events.csv` — `SILENCE` (пакети зникли; з останніми показниками), `RESUMED`, `REBOOT` (змінився `BootKey`).

**На сервері** у `C:\CrashMonitor\Config\config.json` (від адміністратора) і перезапуск монітора:
```json
"EnableUdpHeartbeat": true,
"UdpHeartbeatHost": "<IP приймача>",
"UdpHeartbeatPort": 514,
```

## Публікація в новий Git-репозиторій

Якщо ви створюєте новий репозиторій або клонуєте проєкт на чисту систему:

1. **Регламент повідомлень комітів (Conventional Commits):**
   Використовуйте стандартний формат `type(scope): description`.
   Приклад першого коміту:
   ```bash
   git init
   git add .
   git commit -m "feat(core): initial release of CrashMonitor v2 crash investigation platform"
   git branch -M main
   git remote add origin https://github.com/<owner>/CrashMonitor.git
   git push -u origin main
   ```

2. **Захист від блокувань та сміття:**
   Файли результатів роботи, дампів та логів (`Evidence/`, `Backups/`, `Exports/`, `*.zip`) вже додані до `.gitignore` і не потраплятимуть у коміти.

3. **Увімкнення pre-commit hook у кожному новому клоні:**
   Git не активує хуки з репозиторію автоматично. Один раз після клонування виконайте в корені проекту:
   ```bash
   git config core.hooksPath .githooks
   ```
   Хук потребує Git for Windows (вбудований `sh`) і `powershell.exe` або `pwsh`. Якщо PowerShell не знайдено, хук виводить попередження і пропускає перевірку.
